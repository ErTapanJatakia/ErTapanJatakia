The official Baseline Level 2 set contains 19 controls. The assessment uses the current official criteria version shown above. The current 15 Met results include controls newly evidenced by repository automation and documentation. Three controls remain Partial pending exact collaborator role evidence and owner-side activation of private vulnerability reporting. The single N/A control is conditional on discovery of a vulnerability; no advisory is fabricated.

**Level eligibility caveat:** OpenSSF describes Level 2 as intended for code projects with at least two maintainers and a small number of consistent users. The repository has an owner and an owner-confirmed collaborator, but the collaborator's maintainer responsibilities and the project's consistent-user profile have not been established in the evidence available for this assessment. This register assesses the 19 controls; it does not claim that the project has independently demonstrated Level 2 eligibility.

## Evidence and scope guardrails

- This is the official **Baseline Level 2** control set (19 controls), not the OpenSSF Passing/Silver/Gold badge series.
- The official criteria version used is `v2026.08.28`; reassess if OpenSSF changes the criteria.
- The repository includes Ruby validation utilities and GitHub Actions automation as released source/configuration assets, but no end-user application runtime, compiled binary or deployable service. Build/toolchain instructions, system design and external interfaces now document the actual automation assets; they do not claim an application build.
- DCO sign-off and GPG signing are separate controls. The DCO validator is enforced through the existing required Major change validation check; the one-time adoption PR and history predating adoption are grandfathered.
- The current main ruleset has seven required checks and no bypass actors. The required Major change validation job now depends on successful VEX regression tests and DCO validation for every pull request; QA-06.01 is therefore Met.
- The security policy now publishes acknowledgement, triage and progress-update targets. These are response targets, not a guaranteed remediation SLA.
- The access governance policy now contains a public-safe owner/collaborator role inventory. The collaborator's exact account identifier, effective role and separate secret/release scope remain unrecorded in public evidence; GV-01.01 and GV-01.02 remain Partial pending owner confirmation.
- The connected GitHub integration cannot verify the account-level MFA setting, Private Vulnerability Reporting toggle, or full collaborator/team roster. The workflow permission baseline is verified from all maintained workflow files; private reporting remains Partial until the owner enables and verifies the feature.
- The owner-reported clean vulnerability/malware view is time-bound and must not be converted into a perpetual assertion of zero vulnerabilities. OSPS-VM-04.01 remains N/A only because no confirmed vulnerability is currently known; publish an advisory if one is discovered.

## Reassessment triggers

Reassess when the collaborator's effective role and sensitive-resource scope are confirmed, private vulnerability reporting is enabled and tested, a vulnerability is discovered, the repository introduces an application runtime or compiled asset, or the official criteria version changes.
