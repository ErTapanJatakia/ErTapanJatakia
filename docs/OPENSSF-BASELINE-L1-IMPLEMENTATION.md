## Evidence and scope guardrails

- This is the official **Baseline Level 1** control set (24 controls), not the OpenSSF Passing/Silver/Gold badge series.
- The source criteria version used is `v2026.08.28`; reassess if the official criteria version changes.
- The active ruleset has a pull-request requirement, branch-deletion protection, no bypass actors and seven required checks. The ruleset is the evidence for primary-branch enforcement.
- The repository is a profile/documentation and automation project. Do not invent application user guides, application dependency manifests, runtime tests, or software build evidence where no application exists.
- A GPG-signed commit/tag is not the same as DCO sign-off or mandatory signed commits.
- MFA and collaborator-count evidence are owner attestations; the effective collaborator permission (`read`) and ruleset configuration are independently confirmed through GitHub APIs. Reconfirm account MFA and access roster whenever repository access changes.
- The repository's security contacts are documented, but the GitHub Private Vulnerability Reporting setting is not independently verified by the connected integration.
- The GitHub Release object is not API-reported as immutable. The signed tag is verified and protected; those are separate properties.
- The three N/A controls are conditional and remain N/A because the repository does not currently release end-user software, use an application dependency manifest, or comprise multiple authoritative codebases.

## Cross-level evidence alignment

The repository's common evidence set is maintained across the [Level 2](OPENSSF-BASELINE-L2-IMPLEMENTATION.md) and [Level 3](OPENSSF-BASELINE-L3-IMPLEMENTATION.md) registers. The Level 2 remediation adds DCO enforcement, per-PR automated regression testing, documented build/toolchain instructions, repository automation design/interface inventories and coordinated vulnerability disclosure response targets. These additions do not change Level 1 applicability where its own criterion is conditional on an application runtime or package-management system.

## Reassessment triggers

Reassess when account MFA or collaborator access changes, new workflows/inputs are introduced, new official domains/distribution channels are added, software functionality or package manifests are introduced, multiple authoritative codebases are added, or the official OpenSSF criteria version changes.
